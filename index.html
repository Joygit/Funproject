What is a Network?

The absolute foundation — understand what networks are, why they exist, and how data travels.

A computer network is two or more devices connected so they can exchange data and share resources. Every cloud concept — including all of Azure — is built on top of these fundamentals.

📤 Communication

Send emails, stream video, make calls. Data broken into packets, routed, reassembled at destination.

🗄 Resource Sharing

Share printers, storage, internet connections. One physical resource serves many users.

☁ Cloud Foundation

Azure, AWS, GCP are giant networks of networks. Every VM, database, and API call travels over network infrastructure.

WAN Technologies Deep Dive

MPLS (Multi-Protocol Label Switching)

Labels packets instead of IP routing. Deterministic paths, low latency, used by enterprises for site-to-site WAN. Azure bridges via ExpressRoute.

Leased Line / Dedicated Circuit

Private physical circuit between two sites. Always-on, guaranteed bandwidth. Expensive but very reliable. Basis of ExpressRoute.

Internet VPN (IPsec)

Encrypts traffic over public internet. Cheaper than leased lines. Used for Azure S2S VPN Gateway connections.

SD-WAN

Centralised control over multiple WAN links. Intelligent path selection. Azure Virtual WAN is Microsoft's SD-WAN service.

VLAN — Virtual LAN

VLANs logically segment a physical network into isolated broadcast domains. Devices in different VLANs cannot communicate without a Layer-3 router (or L3 switch).

💡 In Azure, Subnets serve the same purpose as VLANs — logical segmentation within a VNet. NSGs provide the access control equivalent of VLAN ACLs.

Routers & Switches — Deep Dive

Understand how routers make path decisions and how switches learn and forward frames.

Router — Layer 3 Device

A router connects different networks and decides the best path for packets based on destination IP addresses and routing tables.

Routing Table Components

ColumnMeaningExample
DestinationTarget network/host10.0.2.0/24
Next HopNext router to forward to192.168.1.1
InterfaceOutgoing porteth0
MetricPath cost (lower = preferred)10
ProtocolHow route was learnedBGP / OSPF / Static / Connected

Routing Protocols

BGP (Border Gateway Protocol)

The internet's routing protocol. Path-vector. Used in Azure ExpressRoute and VPN to exchange routes between on-prem and Azure. Protocol 179.

OSPF (Open Shortest Path First)

Link-state IGP. Calculates shortest path using Dijkstra. Common in enterprise networks. Azure uses BGP externally; OSPF stays on-prem.

Static Routes

Manually configured. Used in Azure UDRs (User Defined Routes) to force-route traffic through firewall or NVA.

Azure System Routes

Auto-created by Azure. Every subnet gets default routes: VNet address space, 0.0.0.0/0 (internet), and service tags. Can be overridden by UDRs.

Switch — Layer 2 Device

A switch forwards Ethernet frames based on MAC addresses. It learns which MAC is on which port and builds a MAC address table (CAM table).

💡 Hub vs Switch: A hub broadcasts to ALL ports — Switch sends only to the correct port based on MAC. This is why switches are used in all modern networks.

IP Addressing — IPv4 & IPv6

Numerical addressing system that identifies every device on a network.

IPv4 Structure

IPv4 is 32 bits, split into 4 octets (8 bits each), written in dotted-decimal.

192. 168. 1. 100
◀── Network Part ──▶ ◀─ Host Part ─▶ 
Decimal:  192      .  168      .  1        .  100
Binary:   11000000 . 10101000 . 00000001 . 01100100
Subnet:   11111111 . 11111111 . 11111111 . 00000000  (/24)
          ← Network bits (24) →           ← Host bits (8) →

IPv6 — Key Facts for AZ-700

128-bit addressing

Written as 8 groups of 4 hex digits: 2001:0db8:85a3::8a2e:0370:7334. Virtually unlimited addresses (3.4×10³⁸).

Azure IPv6 Support

Azure VNets support dual-stack (IPv4 + IPv6). NSGs, Load Balancers, and VMs all support IPv6. ExpressRoute supports IPv6 peering.

CIDR Subnetting — Worked Example

Problem: You have 10.0.0.0/22. Find: network address, broadcast, host range, total IPs, and how to split into 4 equal subnets.
Given:   10.0.0.0/22
Bits:    32 - 22 = 10 host bits
Total:   2^10 = 1024 addresses
Usable:  1022 hosts  (Azure: 1019)

Network:   10.0.0.0
Broadcast: 10.0.3.255
First Host: 10.0.0.1
Last Host:  10.0.3.254

── Split into 4 subnets (borrow 2 bits → /24) ──
Subnet 1:  10.0.0.0/24  → 10.0.0.1  – 10.0.0.254
Subnet 2:  10.0.1.0/24  → 10.0.1.1  – 10.0.1.254
Subnet 3:  10.0.2.0/24  → 10.0.2.1  – 10.0.2.254
Subnet 4:  10.0.3.0/24  → 10.0.3.1  – 10.0.3.254

Block size = 256 - subnet_mask_last_octet
/24 → 256 - 0 = 256  │  /25 → 256-128=128  │  /26 → 256-192=64

Azure Reserved IPs in Every Subnet

.0 — Network Address

Identifies the subnet itself. Cannot be assigned to a VM.

.1 — Default Gateway

Reserved for Azure's default gateway / router for the subnet.

.2 & .3 — Azure DNS

Reserved for Azure DNS service addresses mapped to the virtual network.

.255 — Broadcast

Broadcast address. Azure doesn't support broadcast but reserves this IP.

Minimum Subnet Size

/28 = 16 IPs − 5 reserved = 11 usable. This is Azure's minimum recommended subnet size.

Gateway Subnet

VPN/ExpressRoute Gateway subnet needs at least /27 for redundancy. Microsoft recommends /27 or /26.

Azure Virtual Network (VNet) — Deep Dive

The core isolation boundary in Azure. Everything lives inside a VNet.

An Azure Virtual Network (VNet) is an isolated, private network in Azure. It provides: segmentation, routing, name resolution, and connectivity to internet, on-prem, and other Azure services.

🌐 Address Space

One or more CIDR blocks (e.g., 10.0.0.0/16). Can have multiple, non-overlapping ranges. Must not overlap with on-prem or peered VNets.

📍 Region-Scoped

A VNet lives in ONE Azure region. For multi-region, use VNet Peering or Virtual WAN. A subscription can have up to 1000 VNets per region.

🔒 Isolation

VNets are isolated by default. No traffic flows between VNets unless you explicitly configure Peering, VPN, or ExpressRoute.

🚀 No Downtime Resize

You can add address spaces to a VNet without downtime. However, you cannot shrink or remove a range that is in use by subnets.

User Defined Routes (UDR)

UDRs let you override Azure system routes. Most common use: force-tunnel all traffic through Azure Firewall or a Network Virtual Appliance (NVA).

🎯 Scenario: Force all internet traffic through Azure Firewall

All VMs in snet-web should route internet traffic through Azure Firewall (10.0.0.4) before leaving.

Solution — UDR

1. Create Route Table → Add route: 0.0.0.0/0 → Next hop: Virtual Appliance → 10.0.0.4 (Firewall private IP)
2. Associate Route Table with snet-web
3. On Firewall subnet: add route 0.0.0.0/0 → Internet (prevents routing loop)

Network Security Groups (NSG) & Application Security Groups (ASG)

The primary access control mechanism in Azure networking.

NSG — Network Security Group

An NSG is a stateful L4 firewall with inbound and outbound rules. It can be associated with a subnet or a NIC (or both). Rules are evaluated by priority (lower number = higher priority).

Application Security Groups (ASG)

ASGs allow you to group VMs by application role and reference them in NSG rules — without managing individual IP addresses.

Example without ASG: Allow port 80 from 10.0.1.4, 10.0.1.5, 10.0.1.6 to 10.0.2.4, 10.0.2.5
Example with ASG: Allow port 80 from asg-web to asg-app — VMs join ASGs, rules auto-apply.

NSG

VS

Private Endpoints

Bring Azure PaaS services into your VNet with a private IP — eliminating public internet exposure.

What is a Private Endpoint?

A Private Endpoint is a network interface with a private IP address from your VNet, mapped to a specific Azure PaaS resource (Storage Account, SQL Database, Key Vault, etc.). Traffic to the PaaS service stays within the Microsoft network — it never traverses the public internet.

Supported Services (Common)

Storage

Blob, File, Queue, Table, DFS

SQL / Cosmos

Azure SQL, SQL MI, Cosmos DB

Key Vault

Secrets, keys, certs via private IP

App Services

Web Apps, Function Apps, API Mgmt

Private Endpoint DNS Configuration

Critical for AZ-700: When you create a Private Endpoint, you MUST configure DNS so that the public FQDN of the service resolves to the private IP inside your VNet.

Example: mystorageacct.blob.core.windows.net normally resolves to public IP.
With PE + Private DNS Zone (privatelink.blob.core.windows.net), it resolves to 10.0.5.4 inside the VNet.

DNS Resolution Flow

VM queries: mystorageacct.blob.core.windows.net
  → Azure DNS (168.63.129.16)
  → Resolves CNAME: mystorageacct.privatelink.blob.core.windows.net
  → Private DNS Zone: privatelink.blob.core.windows.net
  → Returns: 10.0.5.4 (Private Endpoint IP)
  → Traffic flows entirely within Azure backbone ✅

Private Link Service

Expose YOUR service privately to other VNets or customers — the provider side of Private Link.

Private Endpoint (Consumer)

YOU consuming a service (Microsoft PaaS or partner). You create a PE in YOUR VNet. You get a private IP for the remote service.

VS
Private Link Service (Provider)

YOU exposing YOUR service to others. You deploy behind a Standard Internal LB. Customers create PEs pointing to your Private Link Service.

Azure Load Balancer (ALB)

Layer 4 TCP/UDP load balancer for distributing traffic across backend pools.

Public Load Balancer

Frontend has a Public IP. Distributes inbound internet traffic to VMs. Also provides outbound SNAT for backend VMs to reach internet.

Internal Load Balancer (ILB)

Frontend has a Private IP within a VNet. Used for internal workloads — app tier distributing to DB tier, for example.

⚠️ Basic SKU is being retired. Always use Standard SKU for new deployments.

Load Balancer Components

Frontend IP Configuration

The IP address (public or private) that clients connect to. Can have multiple frontends on one LB.

Backend Pool

VMs or VMSS instances that receive traffic. VMs must be in the same VNet. Standard LB supports VMs across availability zones.

Health Probe

Checks if backend instances are healthy. TCP, HTTP, or HTTPS. Unhealthy backends are removed from rotation. Check every 5–15 seconds.

Load Balancing Rules

Maps frontend IP:port to backend pool:port. Session persistence options: None (5-tuple hash), Client IP, Client IP+protocol.

Inbound NAT Rules

Maps a specific port on frontend IP to a specific VM. Used for RDP/SSH access (e.g., frontend:50001 → vm1:3389).

Outbound Rules

Standard SKU: explicitly configure SNAT for backend pool. Avoids SNAT port exhaustion by allocating more ports per instance.

VPN Gateway — Site-to-Site & Point-to-Site

Encrypted hybrid connectivity between on-premises networks and Azure over the internet.

VPN Gateway Types

Site-to-Site (S2S)

Permanent IPsec/IKE tunnel between on-prem VPN device and Azure VPN Gateway. Used for branch office connectivity.

Point-to-Site (P2S)

Low-latency, high-bandwidth private connectivity between VNets using Azure backbone.

Regional VNet Peering

Two VNets in the SAME Azure region. Traffic stays on Microsoft backbone, sub-millisecond latency. No gateway needed.

Two VNets in DIFFERENT Azure regions. Also on Microsoft backbone. Small data transfer charge applies.

Hub-Spoke Architecture

The gold-standard enterprise Azure network topology — centralised security with isolated workloads.

Architecture Overview

The Hub VNet contains shared services: Azure Firewall, VPN/ER Gateway, Bastion, DNS. Spoke VNets contain workloads. Spokes peer with the hub but NOT with each other. All inter-spoke traffic routes through the hub firewall.

Azure NAT Gateway

Managed outbound-only NAT for predictable, scalable internet egress from private subnets.

Why NAT Gateway?

VMs without public IPs need outbound internet. Default outbound SNAT via Load Balancer has limited SNAT ports (1024/VM). NAT Gateway provides up to 64,512 SNAT ports per public IP and supports up to 16 public IPs.

Key Features

Outbound only (no inbound) · Zone-redundant · 64,512 ports per IP · Up to 16 public IPs → 1M+ SNAT ports total · Replaces SNAT on Load Balancer for outbound

SNAT Port Exhaustion — Scenario

⚠️ Problem: SNAT Port Exhaustion on Load Balancer

100 VMs behind a Standard LB with one public IP. Each VM gets ~1024 SNAT ports. Under heavy outbound load, connections start failing with connection timeout errors.

Solution

1. Create NAT Gateway → assign 2 Public IPs (128,000 SNAT ports total)
2. Associate NAT Gateway with the subnet
3. NAT Gateway takes precedence over LB outbound rules for that subnet
4. Each outbound flow gets a unique SNAT port from the large pool

Troubleshooting Scenarios

Real-world scenarios with step-by-step diagnosis and resolution.

🔴 Scenario 1: VM cannot reach the internet

Symptoms: VM can ping other VMs in VNet, but curl/ping to 8.8.8.8 fails.

Diagnosis Steps:
1
Check NSG outbound rules

Network Watcher → IP Flow Verify: Source=VM IP, Direction=Outbound, Dest=8.8.8.8:80. If Deny → find blocking rule name → fix NSG.

2
Check Route Table (UDR)

Network Watcher → Next Hop: Source VM, Dest=8.8.8.8. If Next Hop = None or wrong VirtualAppliance → UDR issue.

3
Check if UDR forces to Firewall

If traffic goes through Azure Firewall, check Firewall application/network rules. Firewall may be blocking without an allow rule for 0.0.0.0/0.

4
Check NAT Gateway / Public IP

If VM has no public IP and no Load Balancer and no NAT Gateway → no outbound SNAT. Add NAT Gateway to subnet.

🔴 Scenario 2: On-prem cannot reach Azure VM over VPN

Symptoms: VPN tunnel shows "Connected" in Azure portal, but pinging Azure VM from on-prem fails.

1
Verify tunnel is connected

Portal → VPN Gateway → Connections → Status should be "Connected". If "Not connected" → check IKE/IPsec parameters match on-prem VPN device.

2
Check Local Network Gateway (LNG)

LNG address space must include ALL on-prem subnets trying to reach Azure. If on-prem has 192.168.10.0/24 not listed → add it.

3
Check Azure VM NSG

NSG on VM NIC or subnet: Inbound rule must allow traffic from on-prem subnet (192.168.0.0/16) on required ports.

4
Check Azure VNet address space in LNG

LNG on Azure side must have the correct on-prem address prefix. Also check on-prem device has a route for Azure VNet (10.0.0.0/16) pointing to tunnel.

5
Check UDR

If subnet has UDR, ensure it doesn't accidentally override the VPN route. Routes to on-prem prefixes must point to VirtualNetworkGateway, not a NVA.

🔴 Scenario 3: Private Endpoint — VM cannot resolve PaaS FQDN to private IP

Symptoms: Private Endpoint created for Storage Account, but nslookup still returns public IP.

1
Check Private DNS Zone exists

Private DNS Zone must be privatelink.blob.core.windows.net (exact name). Zone must have an A record mapping to PE private IP.

2
Check VNet Link

Private DNS Zone → Virtual Network Links → VNet must be linked. Auto-registration can be off — it only matters for VM hostnames, not PE records.

3
Verify A record in zone

Private DNS Zone → Record Sets → Should see A record: mystorageacct → PE private IP (10.0.5.4). If missing, was created manually? Or "Integrate with private DNS zone" not selected during PE creation?

4
Test resolution

From VM: nslookup mystorageacct.blob.core.windows.net. If returns public IP → DNS not linked. If returns 10.x.x.x → working. Also check NSG on PE subnet allows traffic.

🔴 Scenario 4: Hub-Spoke — Spoke VMs cannot communicate with each other

Symptoms: Spoke1-VM and Spoke2-VM both peer with hub, but cannot ping each other.

1
Check Peering settings

Hub-Spoke1 peering: "Allow forwarded traffic" = ON on hub side. Spoke1-Hub peering: same ON. Same for Spoke2.

2
Check UDR on Spokes

Spoke1 UDR: route for Spoke2 prefix (10.2.0.0/16) → Next Hop: Virtual Appliance → Firewall IP (10.0.1.4). Same on Spoke2 for Spoke1 prefix.

3
Check Firewall rules

Azure Firewall Network Rules: Allow source=10.1.0.0/16, dest=10.2.0.0/16, any port → Allow. Without this rule, firewall drops inter-spoke traffic.

4
Check Spoke NSGs

Spoke1 subnet NSG: Allow inbound from 10.2.0.0/16. Spoke2 same. Without this, traffic reaches VM subnet but is blocked by NSG.

🔴 Scenario 5: App Gateway returns 502 Bad Gateway

Symptoms: Application Gateway frontend responds with 502 to all requests.

1
Check backend health

App Gateway → Backend Health → shows each backend VM health status. Unhealthy = red. Check specific error (TCP timeout, HTTP 400, etc.).

2
NSG on backend subnet

NSG must allow: source = GatewayManager (service tag) on port 65200-65535 (management). Also allow App Gateway subnet IP range on backend port (80/443).

3
Health probe misconfiguration

Custom probe: path, port, protocol must match what the backend serves. If backend serves HTTP but probe uses HTTPS → probe fails → 502.

4
Backend not listening

SSH/RDP into backend VM. Verify web server is running: sudo systemctl status nginx or netstat -tlnp. Verify it listens on correct port.

Deploy VMs in Azure Network — Full Walkthrough

Complete step-by-step deployment of a 3-tier application in an Azure VNet.

Architecture Goal

Deploy a 3-tier app: Load Balancer → 2x Web VMs (snet-web) → Internal LB → 2x App VMs (snet-app) → SQL VM (snet-db), all within vnet-prod (10.0.0.0/16), with NSGs and Azure Bastion for management.

Step 1: Create Resource Group & VNet

az group create --name rg-prod --location eastus

az network vnet create \
  --name vnet-prod \
  --resource-group rg-prod \
  --address-prefix 10.0.0.0/16 \
  --location eastus

Step 2: Create Subnets

az network vnet subnet create --name AzureBastionSubnet \
  --vnet-name vnet-prod --resource-group rg-prod --address-prefix 10.0.0.0/26

az network vnet subnet create --name snet-web \
  --vnet-name vnet-prod --resource-group rg-prod --address-prefix 10.0.1.0/24

az network vnet subnet create --name snet-app \
  --vnet-name vnet-prod --resource-group rg-prod --address-prefix 10.0.2.0/24

az network vnet subnet create --name snet-db \
  --vnet-name vnet-prod --resource-group rg-prod --address-prefix 10.0.3.0/24

Step 3: Create NSGs

# Web NSG — allow HTTP/HTTPS from internet, deny all else inbound
az network nsg create --name nsg-web --resource-group rg-prod
az network nsg rule create --nsg-name nsg-web -g rg-prod \
  --name AllowHTTP --priority 100 --direction Inbound \
  --source-address-prefixes Internet --destination-port-ranges 80 443 \
  --protocol Tcp --access Allow

# App NSG — allow 8080 only from web subnet
az network nsg create --name nsg-app --resource-group rg-prod
az network nsg rule create --nsg-name nsg-app -g rg-prod \
  --name AllowFromWeb --priority 100 --direction Inbound \
  --source-address-prefixes 10.0.1.0/24 --destination-port-ranges 8080 \
  --protocol Tcp --access Allow

# Associate NSGs
az network vnet subnet update --name snet-web --vnet-name vnet-prod \
  -g rg-prod --network-security-group nsg-web
az network vnet subnet update --name snet-app --vnet-name vnet-prod \
  -g rg-prod --network-security-group nsg-app

Step 4: Deploy Web VMs

# Create VM (no public IP — will use Bastion)
az vm create \
  --resource-group rg-prod \
  --name vm-web01 \
  --image Ubuntu2204 \
  --size Standard_B2s \
  --vnet-name vnet-prod \
  --subnet snet-web \
  --public-ip-address "" \
  --nsg "" \
  --admin-username azureuser \
  --generate-ssh-keys

# Repeat for vm-web02 (same subnet, gets 10.0.1.5)

Step 5: Create Public Load Balancer (Web Tier)

az network lb create --name lb-web --resource-group rg-prod \
  --sku Standard --location eastus \
  --frontend-ip-name fe-web --public-ip-address pip-lb-web

az network lb address-pool create --lb-name lb-web -g rg-prod \
  --name be-web

az network lb probe create --lb-name lb-web -g rg-prod \
  --name hp-http --protocol Http --port 80 --path /health

az network lb rule create --lb-name lb-web -g rg-prod \
  --name rule-http --protocol Tcp --frontend-port 80 --backend-port 80 \
  --frontend-ip-name fe-web --backend-pool-name be-web \
  --probe-name hp-http

# Add VMs to backend pool via NIC
az network nic ip-config address-pool add \
  --nic-name vm-web01VMNic --ip-config-name ipconfig1 \
  -g rg-prod --lb-name lb-web --address-pool be-web

Step 6: Deploy Azure Bastion

az network public-ip create --name pip-bastion --resource-group rg-prod \
  --sku Standard --location eastus --allocation-method Static

az network bastion create --name bastion-prod --resource-group rg-prod \
  --vnet-name vnet-prod --public-ip-address pip-bastion \
  --location eastus --sku Standard
